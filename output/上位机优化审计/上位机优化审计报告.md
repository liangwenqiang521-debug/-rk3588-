# 上位机优化审计报告

> 审计范围：main.py / page_detect.py / tcp_bridge.py / serial_bridge.py / db.py / infer.py / widgets.py / utils.py / logger.py / config.py / page_history.py / page_log.py（核心链路约 6,100 行）
> 审计日期：2026-09-21 · 方法：逐文件人工精读，所有结论均带代码位置

---

## 总评

上位机整体架构是健康的：背压（MAX_INFLIGHT + ack）、防膨胀（MAX_ROWS / disk_guard）、
crash guard、NG 节流门控这些"防坑机制"都在位，而且大部分都有注释说明踩坑历史。
**剩下的问题集中在三类：GUI 线程被塞了阻塞调用、几处数据正确性隐患、长期运行的健壮性缺口。**

---

## P0 · 立刻修（5 项，均为小改动）

### 1. CPU 采样阻塞 UI 线程 100ms —— 最明显的规律性卡顿

- **位置**：`utils.py:178` `cpu_percent(interval=0.1)`
- **调用方**：`main.py` 状态栏定时器（3s 周期）**和** `page_log.py:156` 系统状态定时器（3s 周期）各调一次
- **后果**：每 3 秒两次、每次 100ms 的界面冻结，与检测帧渲染叠加时肉眼可见掉帧
- **修法**：`psutil.cpu_percent(interval=None)`（非阻塞，按上次调用间隔计算）。
  第一次调用返回 0.0 无妨，下一个周期就有值。**一行改动。**

### 2. NG 蜂鸣阻塞 UI 300ms

- **位置**：`utils.py:41` `winsound.Beep(1000, 300)` —— 同步播放
- **后果**：边缘流持续 NG 时（2s 节流一帧），每 2 秒卡 UI 300ms；和 #1 叠加雪上加霜
- **修法**：`winsound.PlaySound(..., winsound.SND_ASYNC)` 或把 Beep 丢进 `threading.Thread(daemon=True)`。
  顺带可实现可配置的报警音文件。**几行改动。**

### 3. 存图文件名随机数碰撞 —— NG 证据会被静默覆盖

- **位置**：`page_detect.py:1756 / 1771 / 1782` 三处 `"cam_%04d.jpg" % random.randint(0, 9999)`
- **后果**：生日悖论下约 118 张后就有一半概率重名，NG 证据图被后到的覆盖且无任何提示。
  **板端 `_weekly_feedback.py` 已经吃过同款亏**（09-20 修成 db_id 前缀），上位机是同一类 bug
- **修法**：文件名用 `时间戳 + 自增序号`（`ng_%Y%m%d_%H%M%S_%03d.jpg`），或入库拿到记录 id 后回填重命名。
  顺带把三类路径（cam_/sample_/占位）统一到一个命名函数。**3~5 行。**

### 4. step 心跳对同一张照片无限重发 —— 统计失真 + UI 阻塞

- **位置**：`page_detect.py` `_edge_step_tick()` → `_send_photo_for_detect(reason="（自动节拍）")`
- **现状**：只要打开过照片，**每个心跳 tick**（500~2000ms）都会：重读文件 → base64 整图 →
  `sendall`（MB 级，全在 GUI 线程）→ `return` 后**永远不发 `cmd=next`**
- **后果**（三连）：
  1. 同一张照片被反复检测、反复计入统计 → **良率/NG 率严重失真**
  2. GUI 线程每次发送阻塞（照片越大越久）
  3. INFO 日志每秒刷一条"已送检照片"
- **修法**：照片送检只该发生在三个时机——打开照片、开始检测、手动"检测下一张"；
  心跳里加 `_photo_sent` 标志（照片路径变化时重置），送过就落到 `cmd=next`

### 5. mock 模式也写数据库 —— 假数据污染真实记录

- **位置**：`page_detect.py` `_fake_frame()` 每帧 `self.db.insert(...)`
- **后果**：模拟演示的随机 NG/OK 混进 `records.db`，历史页良率统计、导出 CSV 全部被污染；
  演示完不清库的话长期数据不可信
- **修法**：模拟模式不写库（最简单），或写内存库 + 检测页加"演示模式"水印角标。
  兼容旧数据的清理：`DELETE FROM records WHERE image_path LIKE '%sample_%'`

## P1 · 排期做（5 项，涉及线程/架构调整）

### 6. 板端断线后无自动重连

- **位置**：`tcp_bridge.py run()` 退出后只发 `connected(False, "已断开")`；
  `page_detect._on_edge_connected()` 里 `_auto_left` 已被清零 → 不重试
- **后果**：板子重启 / 网线闪断后必须手动点"连接 RK3588"；产线场景不可接受
- **修法**：连接成功后进入"看门狗重连"状态：断线 → 灯变黄"重连中" → 3s 退避重连
  （复用现有 `_auto_retry` 机制，把 `_auto_left` 语义从"仅开机"扩展为"断线后"）

### 7. `send_detect_image` 在 GUI 线程同步 sendall

- **位置**：`tcp_bridge.py:123`；调用链 `_send_photo_for_detect`（GUI 线程）
- **后果**：即使修了 #4，单次发送仍可能卡 UI 数百 ms；TCP 背压时更久
  （板端 5s 超时窗口内 sendall 全程挂着）
- **修法**：桥接线程加发送队列（`queue.Queue` + 线程内 `select`/非阻塞发送），
  GUI 只负责入队，立即返回

### 8. 录像帧写入（MJPG 编码）在 GUI 线程

- **位置**：`page_detect.py` `_on_camera_frame`（相机路径）与 `_record_edge_frame`（边缘路径）
- **后果**：30fps 相机录制时每帧编码写盘都在 UI 线程，掉帧 + 界面卡
- **修法**：VideoWriter 移到独立 QThread，帧走队列（满则丢旧保新）

### 9. DB 每条 insert 一次 commit（fsync）在 GUI 线程

- **位置**：`db.py:47` `self.conn.commit()` 每条一提交
- **后果**：边缘流 NG 0.5s/条、OK 1s/条，每次 fsync 几~几十 ms；检测高峰时叠加表格刷新
- **修法**：写入队列 + 后台 writer 线程，攒批 commit（如 0.5s 或 20 条一次）；
  顺带开 `PRAGMA journal_mode=WAL`。注意保持防膨胀 trim 逻辑

### 10. 相机 worker 每帧都 JPEG 编码

- **位置**：`page_detect.py:99` `cv2.imencode(".jpg", frame)` 30fps 全编
- **后果**：`_cur_frame_bytes` 只有 NG 落盘/存证时才用，白白烧 CPU
- **修法**：只保留 `latest_bgr`，需要时（NG 确认 / 点存证）再编码

- `stats_received` 信号在检测页的桥接上从未连接（板端 stats 帧被空投）——当前 NPU 页自建连接所以无碍，

## 附：为什么这些值得写进论文/汇报

这份清单本身就是"边缘部署上位机工程化"的素材：GUI 线程纯净性（阻塞调用审计）、
背压与丢帧策略、IO 节流门控、断线自愈——都是工业 HMI 的真实工程问题，
比单纯罗列功能更有说服力。修完 P0/P1 后，PPT 第 8 页（板端部署与工程指标）可以补一行
"上位机侧：UI 零阻塞渲染、断线自愈、证据链文件名可追溯"。
